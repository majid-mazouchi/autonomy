The Token Kit, Explained

What was built to make a VS Code Copilot setup cheaper without making it dumber, why each piece exists, and how to tell whether it is working. In plain words.

By Majid Mazouchi · September 5, 2026

Three facts that explain everything

Every time you send a message to Copilot, it does not just send your message. It sends the whole conversation so far, plus every instruction file it has loaded, plus a description of every tool it could call. The model reads all of that from scratch, every single time, and you pay for every word it reads.

Once you know that, three facts do most of the explaining.

Fact one: everything in the conversation is sent again on every turn. A 3,000-line log that a tool printed on turn two is re-sent on turn three, turn four, and every turn after until it is cleared or compacted. It is not "in memory". Some of it may be re-read at the cheaper cached rate if the harness caches history, but it still occupies the window, and the window filling up is what makes a session that felt fine at turn five feel slow at turn twenty.

Fact two: words the model writes cost five to eight times more than words it reads. On every model Copilot offers, output is priced several times above input. So a model that reads a lot and writes a little is cheap, and a model that rewrites a whole file to change one line is expensive.

Fact three: the cheapest model costs about fifty times less than the most capable one. Copilot now bills per token at each model's own rate. Sending a "find where this function is called" task to the most capable model is like hiring a surgeon to take your temperature.

The kit is a set of small files that act on those three facts. Nothing in it is clever. Most of it is discipline written down in a form Copilot has to read, plus a few pieces that measure whether the discipline is working.

How Copilot bills now

Since June 2026, Copilot Business and Enterprise plans bill in AI credits. One credit is one cent. Each interaction consumes tokens, and each token is priced by the model that processed it. There are four prices per model: fresh input, cached input, cache write, and output. Included allowances are pooled across the organization; usage past the allowance is billed at the listed rates.

"Cached input" is the important one. If the front of your request is identical to the front of your last request, the provider does not re-process it. It charges about a tenth of the fresh price. So the long stable stuff, the instructions and tool descriptions, is nearly free if it stays identical and stays at the front. It becomes expensive the moment something in it changes on every call.

The layers of the kit

VS Code lets you customize Copilot with a handful of file types, and each one loads at a different moment. The kit uses all of them, and picking the right layer for each rule is most of the design.

The rule of thumb that falls out: put a rule in the cheapest layer that still gets it followed. A rule that only matters for Python files goes in a scoped instruction, not the harness. A procedure that only matters when auditing goes in a skill, not the harness. A rule that absolutely must hold goes in a hook, because hooks cannot be forgotten.

With eight skills, loading every body on every call would cost about 4,800 tokens; loading name and description only, plus the one or two bodies that match, costs about 1,300. Copilot already loads bodies on demand, so the eager bar is a comparison point rather than a saving the kit creates. What the kit adds is keeping descriptions accurate so the right body wakes up and the wrong ones stay asleep, and a linter that catches overlap.

The seven skills

A skill is a procedure Copilot follows when the task matches its description. The description is the important part: it is the only thing Copilot reads when deciding whether to wake the skill up, so each one says both what the skill does and when to use it.

token-budget

Wakes up when: something is slow or expensive, context is full, or you ask which fix to try first

The decision layer. Given a symptom, it names the lever and says what order to try things in. It also holds the rule that overrides everything else: if something is stable across calls, cache it, do not compress it. Detailed material lives in four reference files that stay on disk until needed.

Body 821 tok · references 4 files, read on demand

kit-audit

Wakes up when: you ask what is eating your tokens, or before adding a skill, agent, or MCP server

Says one thing: measure before changing anything. Then tells Copilot how to run the audit script and how to read its report. The intuitive target is usually the wrong one, and this skill exists to stop the guessing.

Body 546 tok · ships audit_kit.py

lean-output

Wakes up when: editing files, when responses restate too much, or when output keeps failing to parse

Discipline for the expensive tokens, the ones the model writes. Change a file with a small patch, not a rewrite. Check that the patch will match before sending it, because a failed match costs a whole retry. Say what changed and stop. No preamble, no summary of a diff you can read yourself.

Body 476 tok

handoff-contract

Wakes up when: one agent hands work to another, or when a delegation came back wrong

Two short forms. A brief going down: objective, scope, what not to touch, pointers to inputs (paths, not contents), what to deliver, how it will be checked, a turn budget, and a tier. A result coming up: status, confidence, tier used, a path to the full findings, and an abstract under 200 tokens. The point is that payloads never travel in messages. They sit on disk and pointers travel instead. Saving to a file does not remove something from context once it has been read this session; what it prevents is re-reading, and re-sending after a reset.

Body 724 tok · 1 reference on how delegations fail

skill-hygiene

Wakes up when: creating or editing a skill, or when one fires too often or never

How to write a skill that costs little and triggers reliably. Description first, because that is what the router matches. Body small, because it is paid every time. Anything deterministic in a script, because scripts are free at context level. It ships a linter that checks all of this.

Body 723 tok · ships skill_lint.py

session-state

Wakes up when: a task will take more than a few turns, or after the context was reset

The plan and the findings live in files under .copilot-state/, not in the conversation. A file is read once when needed; the conversation is re-sent on every turn. After a reset, read plan.md and nothing else until the plan points at something.

Body 466 tok

model-routing

Wakes up when: choosing a model for an agent, delegating, or when something is expensive

Which tier of model a task deserves, and how to price the difference. Covered in its own section below, because it is the largest lever in the kit.

Body 953 tok · ships assign_models.py and a dated pricing table

The three agents

An agent is a persona you pick from the dropdown. It carries its own instructions, a list of tools it is allowed to use, and a pinned model. Restricting the tools matters more than it sounds: an agent with no tool list may carry the description of every tool you have connected, on every call.

scout

Tier T0, the cheapest model · read-only tools

Finds things. Returns a short summary and path:line pointers, never pasted file contents. Searches narrow first, stops when it has the answer, and asks one question rather than reading ten more files. If unsure, it says so rather than guessing, because a confident wrong location costs more than an honest gap. After it finishes, a button offers to hand its findings to the orchestrator.

lean-orchestrator

Tier T2, a capable mid-range model · can edit, run, and delegate

Plans and delegates. Writes the plan to a file first, delegates bounded work to scout using the handoff form, reads abstracts before full artifacts, and does the synthesis itself because that is where contradictions need to be visible at once. When a cheap agent comes back unsure, it re-delegates one tier up and writes down why.

token-auditor

Tier T1 · runs scripts, never edits

Runs both measurement scripts, reports the top three sinks, checks each candidate fix against the anti-patterns list, and proposes exactly one change as a diff. Applying happens through a handoff to the orchestrator, which then re-runs the audit and reports what actually moved. It cannot be pulled in as a subagent by accident.

Hooks: the part that cannot be forgotten

Everything above is advice. Copilot reads it and usually follows it. Hooks are different: they are shell commands that VS Code runs before or after a tool call, whether or not the model remembers to. Instructions are a company policy; hooks are the seatbelt.

The kit ships two.

The read guard runs before every tool call. If the agent is about to read a file longer than 400 lines with no line range, the hook does not block it; it asks. You see the file size and a one-line reason before paying for it. Ranged reads and small files pass silently.

Figure 3The read guard, live

The token estimate uses about 11 tokens per line of code. A 900-line file read whole is roughly 10,000 tokens, and by fact one it is re-sent on every later turn of the session. The guard exists to make that cost visible at the moment it is about to be paid.

The ledger runs after every tool call and appends one line to a local file: which tool, how big its arguments were, how big its result was, which tier was configured. Nothing leaves your machine. It is a diagnostic for finding oversized tool results, and it is the only part of the kit that records something that actually happened. It is not a billing meter: it does not see prompts, generated output, reasoning, cache hits or failed calls. For billed usage, VS Code's OpenTelemetry export reports the resolved model and token counters per model call, and the provider's usage page is the reconciliation source.

Read the scripts first

Hooks run with the same permissions as VS Code. Both scripts are short, fail silently rather than blocking if the input format is unexpected, and are worth reading before you enable them.

Model tiers

This is the biggest lever and the newest part of the kit. Copilot offers around twenty models, and their prices differ by about fifty times. The kit sorts them into four tiers and treats the tier as configuration: a file says which agent runs on which tier, and a script writes that into the agent files.

TierForDefault pickIn / Out per 1M tok
T0Locate, grep, list usages, extract fields, classify, rename, boilerplateGPT-5.4 nano$0.20 / $1.25
T1Bounded edits, test scaffolds, docstringsClaude Haiku 4.5$1.00 / $5.00
T2Multi-file changes, debugging, orchestration, synthesisClaude Sonnet 5$2.00 / $10.00
T3Safety logic, root-cause conclusions, architecture, anything a human trusts without re-derivingClaude Opus 5$5.00 / $25.00

The rule for choosing is not "how important is this" but "would a wrong answer be caught cheaply". If a test or a compiler catches it, route low. If a human has to read it carefully to know it is wrong, route high. And anything under a path you have marked critical runs at T3 regardless, enforced by a scoped instruction that tells a lower-tier agent to stop and hand off.

Design high, generate low, verify high

Because output costs five to eight times input, and because cached input is nearly free, the expensive thing is not a big model reading a lot. It is a big model writing a lot. So the pattern that captures most of the saving is: a T2 or T3 agent writes the plan and the interface, a T0 or T1 agent produces the volume, and a T2 or T3 agent reviews the diff. The expensive model reads a short plan and a diff. The cheap model writes the many lines.

The deferral rule

A cheap model that is unsure must say so and stop, not guess. Every brief to a T0 or T1 agent carries that instruction, and every result carries a confidence field. Low confidence from a cheap tier means: escalate one tier, write down why, do not use the answer. Without this rule, cheap models produce confident wrong output, which is the most expensive failure there is, because someone has to find it.

The two files

.github/models.yaml lists the tiers, the models in each with their rates, which model each tier uses by default, and which paths are critical. .github/agent-tiers.yaml says which agent runs at which tier and which minimum tier each skill needs. Skills cannot pin a model themselves, so the orchestrator reads the skill's minimum when choosing whom to delegate to.

python .github/skills/model-routing/scripts/assign_models.py --root .          # show what would change
python .github/skills/model-routing/scripts/assign_models.py --root . --write  # apply
python .github/skills/model-routing/scripts/assign_models.py --root . --clear --write  # undo

Applying does two things per agent: writes the model line, and adds a hook that tags every recorded tool call with the agent's tier. VS Code does not tell hooks which model is active, so the tier has to come from the agent definition. That tag is what lets the audit price real sessions by tier.

The scripts, and what each one measures

Three scripts. None of them enter the model's context; only their output does. They are the part of the kit that is not advice.

audit_kit.py

Walks your .github folder and works out what loads on every call versus on demand, ranks the sinks by how much of a session they consume, and prices each fix two ways: with the front of the prompt cached, and without. That second comparison is the part worth reading twice. On the kit itself the same fix looks eight times bigger without caching than with it, which is why published "85 percent reduction" figures rarely survive contact with a setup that already caches. It also reads the ledger, prices each agent per call at its tier, and takes a previous run with --compare to show what moved.

skill_lint.py

Checks every skill: is the description long enough to trigger, does it say when to use the skill, is the body oversized, does it point at files that exist, does it have a minimum tier. Then compares every pair of descriptions and flags the ones similar enough that both skills would wake up on the same request, so you pay for two bodies.

assign_models.py

Applies the tier file to the agent files. Dry run by default, shows a diff, writes on request, and undoes cleanly.

Installing it

  1. Copy the .github folder into your workspace root, merging with what you have. If you already have a copilot-instructions.md, take the sections you want rather than replacing it; that file is your cached prefix and keeping it stable matters more than what is in it.
  2. Merge the settings snippet into .vscode/settings.json. It turns on skills and hooks and points VS Code at the hooks folder.
  3. Run the audit and the linter once before changing anything, and keep the JSON output as your baseline.
  4. Check that the four default models in models.yaml are enabled in your organization. If an agent fails to load, the model name is not available; change the default pick and re-run the assignment, or clear the pins.
  5. Edit the critical paths in models.yaml and in critical-paths.instructions.md to match your tree.
  6. Make one change at a time, re-run the audit with --compare, and keep only what lowered tokens per call.

Honest limits

Every number the scripts produce is an estimate. The token counter may be a heuristic if the exact tokenizer cannot load, and it says so in its output. The rates are dated in the registry and will change. The estimate for MCP tool descriptions is a crude multiplication and should be replaced by a real measurement of your serialized request.

The hook input format follows VS Code's documented field names with fallbacks, but if your version differs the scripts fail silently rather than blocking the agent. Check the hooks output channel once after enabling them.

The tier assignments are a starting point. The right tier for a task shape in your codebase is whatever the ledger shows has the fewest retries at the lowest cost, and the kit gives you the ledger so you can find out.

And the kit changes what your setup loads and what your agents write. It does not compress what crosses the wire. If you want that as well, tools exist for it and they compose with this; but fix the source first, because compressing a bloated always-on block is worse than not having the bloat.

Glossary

Token
The unit the model reads and writes and you pay for. Roughly three quarters of an English word, so about 1.3 tokens per word; more tokens per word for code and non-Latin scripts.
Context, context window
Everything the model can see on one call: instructions, tool descriptions, the conversation so far, tool output, your message. It has a size limit, and all of it is billed.
Prefix, cached prefix
The front part of the request that is identical from one call to the next. Providers store it and charge about a tenth of the price to reuse it. Anything that changes per call breaks the cache from that point onward.
AI credit
Copilot's billing unit since June 2026. One credit is one cent. Tokens are priced per model and converted to credits.
Skill
A folder with a SKILL.md file describing a procedure. Copilot reads the name and description always, the body only when the description matches your request.
Agent
A persona defined in a .agent.md file: instructions, an allowed tool list, a pinned model, and buttons to hand off to other agents.
Hook
A shell command VS Code runs before or after a tool call. Deterministic; it cannot be forgotten the way an instruction can.
Tier
A group of models with similar price and capability. The kit uses four. Work is routed to the lowest tier whose mistakes would be caught cheaply.
Handoff
One agent passing work to another. The kit insists this carries pointers and short abstracts, never the payload.
Compaction
Summarizing a long conversation and starting again with the summary, when the context is approaching its limit.
Ledger
The local file the PostToolUse hook writes, one line per tool call. A diagnostic for oversized tool results, not a billing meter.
